## صف‌ها/پیام‌ها، کارهای زمان‌بندی‌شده، و Idempotency

این سند الگوهای توصیه‌شده برای پردازش آسنکرون با صف/پیام‌رسان، زمان‌بندی وظایف، و ایدمپوتنسی عملیات را توضیح می‌دهد. با معماری فعلی (FastAPI, Redis, پیشنهاد RabbitMQ/Kafka در فاز بعد) هم‌راستاست.


### صف‌ها/پیام‌ها (Queues/Messaging)
- اهداف:
  - جداسازی کارهای سنگین/طولانی (آپلود/پردازش تصویر، پیش‌بینی، تولید گزارش) از مسیرهای همگام
  - افزایش تاب‌آوری و مقیاس‌پذیری؛ کاهش latency مسیرهای API
- گزینه‌ها:
  - MVP سبک: Redis Queue/Streams برای حجم کم، سادگی
  - فاز رشد: RabbitMQ (وظایف قابل‌اعتماد) یا Kafka (جریان‌های حجیم/تحلیلی)
- الگوها:
  - Producer API → enqueue Job با payload حداقلی (شناسه‌ها/مسیرها)
  - Worker → pull/consume → اجرا → ثبت نتیجه/وضعیت
  - Retry با Backoff و DLQ (Dead Letter Queue) برای شکست‌های مکرر
  - Visibility/Idempotency: ذخیره شناسه Job و وضعیت جهت عدم اجرای تکراری
- قرارداد Job (نمونه):
  ```json
  {
    "job_id": "job-2025-0001",
    "type": "prediction.run",
    "payload": {
      "patient_id": 123,
      "record_id": 456,
      "model": "alzheimer-v1.0"
    },
    "attempt": 1,
    "created_at": "2025-01-01T10:20:30Z"
  }
  ```
- Observability:
  - متریک‌ها: queue depth، نرخ مصرف، نرخ موفق/ناموفق، میانگین زمان پردازش
  - لاگ ساختاریافته با `job_id`، Trace span برای Job execution


### کارهای زمان‌بندی‌شده (Scheduled Jobs)
- موارد کاربرد:
  - گزارش‌های طولی زمان‌بندی‌شده، آرشیو/Retention، همگام‌سازی‌های Batch، پاک‌سازی لاگ/فایل
- ابزارها:
  - MVP: cron/apscheduler در یک سرویس Worker اختصاصی
  - فاز بعد: سیستم زمان‌بندی توزیع‌شده (Celery beat، Airflow, Cloud Schedulers)
- اصول:
  - Jobها idempotent؛ ثبت آخرین اجرا/نتیجه و قفل توزیع‌شده (Redis lock) برای جلوگیری از اجرای موازی ناخواسته
  - شاخص‌ها/هشدار: مدت اجرا، نرخ شکست، خروجی‌های غیرعادی
  - Runbook: سناریوهای شکست و ازسرگیری امن


### Idempotency (ایدンプوتنسی)
- تعریف:
  - اجرای چندباره یک عملیات بدون ایجاد اثرات جانبی اضافی (نتیجه نهایی یکسان)
- موارد مهم:
  - POSTهای حساس (پرداخت/پیش‌بینی/ایجاد گزارش)، وب‌هوک‌ها، Jobهای آسنکرون
- تکنیک‌ها:
  - Idempotency-Key در کلاینت → ذخیره وضعیت/پاسخ در سرور برای کلید مشخص با TTL
  - Deduplication در لایه Job: جدول/کش `job_id` → وضعیت `pending/running/completed/failed`
  - عملیات دیتابیس: upsert/ON CONFLICT، تراکنش‌های اتمیک
  - وب‌هوک‌ها: استفاده از `event_id` یکتا و ثبت رسیدگی؛ رد تکراری‌ها
- طرح ذخیره‌سازی (نمونه ساده):
  - جدول/کش: `idempotency_keys` → { key, request_hash, response_body, status, created_at, ttl }
  - رفتار: اگر key قبلاً دیده شده و متناظر است → بازگرداندن همان پاسخ


### الگوهای خطا/Retry
- خطاهای موقت (Timeout/5xx): Retry با Backoff و Jitter؛ سقف تلاش‌ها؛ انتقال به DLQ
- خطاهای دائمی (4xx منطقی): بدون Retry؛ ثبت و اعلان
- Circuit Breaker برای مقصدهای ناپایدار؛ Fail-fast و مسیر degradaded


### امنیت و انطباق
- Payload حداقلی؛ عدم ارسال PHI/PII در پیام‌ها مگر ضروری و با رمزنگاری
- امضای پیام‌ها برای کانال‌های برون‌سازمانی؛ TLS end-to-end
- ممیزی Jobهای حساس (چه کسی/چه زمان/چه داده‌ای)


### مسیر پیاده‌سازی پیشنهادی
- فاز 1 (MVP):
  - ماژول Worker ساده با Redis Queue برای: تولید PDF، وظایف آرشیو، همگام‌سازی Batch
  - Idempotency-Key برای وب‌هوک‌ها و POSTهای حساس انتخابی
  - متریک‌های پایه: queue depth، job duration، success/fail
- فاز 2:
  - مهاجرت وظایف پرترافیک به RabbitMQ/Kafka
  - زمان‌بندی توزیع‌شده (Celery beat/Airflow) برای گردش‌های پیچیده
  - DLQ و Runbook‌های کامل
- فاز 3:
  - تریسینگ توزیع‌شده برای Jobها، سیاست‌های پیشرفته Idempotency/Deduplication
